В проекте провёл профилирование с помощью профайлера pprof.

Добавил защищенные роуты для использования веб-интерфейса pprof.

Исслеловал пункты меню профайлера:
- allocs показывает всё выделение памяти за период профилирования
- block показывает где горутины ждут (mutex, chanal, WaitGroup). Необходимо включать "runtime.SetBlockProfileRate(1)"
- cmdline процесс, для которого происходит профилирование
- goroutine показывает все работающие горутины и их текущие стеки
- heap показывает объекты, которые в данный момент живут в куче, и объём памяти, который они удерживают
- mutex показывает блокоровку горутин. Необходимо включать "runtime.SetMutexProfileFraction(1)"
- threadcreate показывает, где в коде создаются новые ОС-потоки

Для получения файлов профилей использовал имитацию нагрузки на геосервис (10 users, 10 adresses, 30 запросов в секунду) файл loadgen.go. CPU профиль (30 секунд). Трейс (30 секунд).

Запуск нагрузочного теста с помощью скрипта "./run_load_test.sh"

Профили trace и profile сохранены в папке profiles.

CPU профиль смотрел командой "go tool pprof profiles/profile; top", а так же открывал граф в браузере "go tool pprof -http=:8081 profiles/profile". 
 
Trace (запись хронологии работы приложения во времени) "go tool trace -http=localhost:8081 profiles/trace".
 
Вывод из данных профилирования программы:
1. Утечек памяти не обнаружено.
2. Утечек горутин не обнаружено.
3. Программа не упирается в CPU.
4. Основным источником аллокаций памяти является JWT-верификация (библиотеки github.com/lestrrat-go/jwx/v2 и github.com/go-chi/jwtauth/v5). При каждом запросе происходит парсинг и верификация токена, что создаёт множество мелких аллокаций (32-480 байт на запрос).
5. Узким местом программы является обращение к API dadata (190ms 40.43%  internal/runtime/syscall.Syscall6). Кеширование результатов даёт существенный прирост к прозводительности программы путем сокращения времени запросов к внешнему API.
